Status: the platform specification was approved on 2026-10-12. Plan 1 (the toolchain and the core of the blackboard) is implemented. Plan 2 (the runtime spike) chose the agent runtime (ADR-006), and live runs confirmed it. Plan 3a built the mechanism check's data and scorer; Plan 3b built the retrospective check command, and the mechanism check passed on 2026-10-14. On 2026-10-14 the author decided to build the rest of Phase 0 before a team adopts the platform (ADR-016); Plan 4 built the registry, Plan 5a the MCP gateway's read path, Plan 5b its board tools and record-only proposals, Plan 6a the audit chain, Plan 6b the LLM gateway, Plan 7a the coordinator's core, Plan 7d-1 `agentswarm serve`, the agent runtime and a fault-injection harness, and Plan 7d-2 the runner in Docker sandboxes. At the checkpoint after Plan 7d, on 2026-11-01, the author decided to keep building (ADR-016). Plan 7b-1 gave each work item its lifecycle: a queue with promotion, close, reopen, auto-close and the kill switch; its branch's end, the final review among it, came on 2026-11-03.

## Implementation

Go, with domain-driven design and interface-driven ports and adapters. See Section 2.2 of the platform specification.

Build and test with `make build`, `make test`, `make test-integration` (needs Docker), `make test-e2e` and `make test-live`. `make test-live` plays one turn of the agent runtime through the LLM gateway against the model vendor: it needs `AGENTSWARM_LIVE_KEY`, the vendor's key, and costs a few cents. Run it, and commit `internal/llm/endpoint/testdata/live-check.json`, whenever the anthropic-sdk-go version changes (`make test` fails until then), and before agents switch model (set `AGENTSWARM_LIVE_MODEL` to the new model).

`make test` also runs the coordinator's interleaving test, in `internal/work/app`, on its default schedules. Two instances, each the real leader over the real coordinator, share in-memory fakes of every store, clock and port, and seeded schedules drive them through acts and previews, lost answers and failed writes, a lease lost in the middle of an act, failed renewals, drains, crashes and takeovers, kill switch rows written out of band, and steps of the database's clock and of each instance's wall clock, forward and back, up to 10 minutes, though the database's clock steps forward by less than the lease's margin within a lease's term; reads also fail, on their own or after a write to the same store has failed (a record store's `Load`, `Active` and `UnstaffedBy`, the board's `Load` and the kill switch's reads, each per instance). The lifecycle's ten invariants are checked each at its own point: the tenth, that nothing runs for a closed item, at every call that starts work, and after every event; most of the others after every event, or after every batch of events in the concurrent mode, and two only once the schedule has settled, that every run alive at an on-row was halted, and that a stopped run leaves nothing running. The default run, 200 sequential schedules of 200 events and 20 concurrent ones from a base seed fixed in code, takes about 8 to 12 seconds under `-race`. The seeds recorded for Plan 7b-1's version of the test no longer replay, since the world now draws more faults. A failure prints its seed, the tail of its event log, the invariant it broke, and the command that runs it again, `go test -race -count=1 -run '^<test>$' ./internal/work/app/ -args -interleave.seed=<seed>`, in the test's own mode: a sequential schedule replays event for event, while a concurrent one replays its choice of events and faults, not their timing, so its command runs it 20 times. The soak run, `go test -race -count=1 -v -timeout 60m -run '^(TestRandomSchedulesKeepTheLifecyclesInvariants|TestConcurrentSchedulesKeepTheLifecyclesInvariants)$' ./internal/work/app/ -args -interleave.for=40m`, runs schedules for 40 minutes, half sequential and half concurrent, from a base seed of the clock's, which each test logs, unless `-interleave.base` gives one.

`agentswarm registry validate --dir DIR` checks a configuration repository against every loader rule; `examples/config/` is a fictional team's repository. `agentswarm registry hash-tools --endpoint URL` prints each of a server's tools with the whole definition that a server registration pins, and its schema hash; `--ca FILE` trusts a CA bundle besides the system roots.

`agentswarm migrate` applies the database's migrations to the database the libpq environment variables name (`PGHOST` and the rest), or to the one `--secrets DIR --database REF` names. Migrations are expand-only: each records the oldest build that can read the schema it leaves, and one that older builds cannot read is refused while an instance holds the lease, unless `--force` is given. `agentswarm serve --deployment FILE` runs one instance of the platform: the coordinator, the leader, which holds the platform's lease, both gateways, and the admin API on loopback, with the deployment file of Plan 7d-1's Contract C1; `examples/deployment.yaml` is a commented example, and `bench/itbench/README.md` runs the mechanism check's investigators on one scenario under serve. Of several instances, one leads at a time, and the others stand by. SIGINT or SIGTERM drains it under the lease it holds; a second signal stops every turn and exits at once. Serve logs at its start the longest its drain can take, as `worstDrain` in its `serve started` line, `1m27s` with the default timings: a supervisor's stop timeout must stay above it. Its runner runs each turn with `agentswarm turn`, the agent runtime, which reads its turn's spec on standard input: in a Docker sandbox, with `runner.kind: docker` (below), or, for development and tests, as a host process, with `runner.kind: process`. The process runner runs turns unsandboxed, so serve allows it only with `runner.unsafeNoSandbox: true`, and only with the gateways' listeners on loopback, since they serve it plain HTTP. `agentswarm inspect --deployment FILE item ID`, `board RUN` or `calls RUN` prints, as JSON lines, what the database holds of an item, a run's board or a run's calls. `agentswarm conclude --board FILE` assesses a recorded board offline. It decodes the file strictly, so a build older than Plan 7d-2 refuses a board whose `turn_unstarted` notice holds a `reason`: conclude such a board with this build or a later one.

Each work item has a lifecycle (spec Section 4.1). Past `lifecycle.investigating` items investigating at once, 3 by default, a new item waits in the queue, and starts in its turn. The admin API acts on items: `POST /v1/items/{id}/promote` starts a waiting item at once, even past the limit by one, or staffs an item that awaits its close with no run; `POST /v1/items/{id}/close` closes an item from any state, and stops its run mid-round; and `POST /v1/items/{id}/reopen` reopens a closed item within `lifecycle.reopenWindow`, 24 hours by default. Each takes an `Idempotency-Key` of 1 to 128 printable ASCII characters, under which a retry answers as the act did, and an optional body, `{"reason": {"code": "...", "text": "..."}, "preview": true}`: a preview takes no key, and answers the act's consequences while it does nothing. An item awaiting its close closes by itself after its work item type's `autoClose.after`, 30 minutes by default. `GET /v1/kill-switch` shows the kill switch, and `POST /v1/kill-switch` turns it on or off, with `{"on": true, "after": <seq>, "reason": {"code": "..."}}`: `after` is the latest row its sender read, 0 before the first, so that a delayed request never undoes a newer one, and the on needs a reason. The on stops every run at once, and staffs no item, while auto-close pauses, until an admin turns it off; the off lists the items the on left unstaffed, which a person promotes. A draining serve still takes the on, recorded under its holding for the next leader to act on. A refusal of these routes is `{"error": "...", "code": "..."}`. `GET /v1/items/{id}` shows an item's place in the queue, why it is not staffed, when it closes by itself, and its close; `/v1/status` shows the kill switch and the queue. A write of the kill switch whose answer is lost may have landed: until a read of the switch settles it, serve starts no work, as if the switch were on, and a promotion answers `503`, to be sent again; close, reopen, previews and reads go on. Serve logs `kill switch unsettled` as this begins and `kill switch settled` when a read ends it, at most a retry wait, 5 seconds by default, once the database answers again. A turn already running or launching when an on-row committed keeps its session until then.

Upgrading to this build: migration 0010 adds the kill switch's table, and no older build can run on the schema it leaves, so stop the older instances, migrate, then start the new build, which is downtime with two instances. A rollback is then a roll forward, or a restore from a backup, which loses what was written since. A restore can also lose an on-row of the kill switch: read the switch after a restore, and turn it on again if an on was lost. The anchor owner's read-only role, with which `agentswarm audit anchor` and `audit verify` read the chain, needs `SELECT` on `kill_switch`. The deployment's `tenant` must be of the anchors' form, 1 to 63 lowercase letters, digits and dashes, the first not a dash, and serve refuses to start while the environment gives `MCPGODEBUG` a non-empty value. The registry now refuses a key value listed inline that holds a character a reader could miss, tab and line feed included: remove any such value from the configuration repository before upgrading, since an open item locked at a commit that holds one cannot rebuild its revision under the new rule. The admin token now authorizes every lifecycle act, promotion, close and reopen, and the kill switch's on and off, besides openings: it acts as an admin, and an on stops every run. Under the process runner a turn runs as serve's user and can read the secrets directory, the admin token's file included, which the Docker runner keeps out of a turn's reach. An older build's `agentswarm conclude` refuses a board that holds a `skill_yanked` notice, for its new field: conclude such a board with this build. The first takeover after the upgrade arms the auto-close of every older item awaiting its close, and those already past their deadline close one by one, just after it.

The Docker runner, on Linux alone, runs each turn in a sandbox: a container of the runtime image the item locked, with no network, which reaches the gateways through two Unix sockets in `runner.docker.sockets`, over TLS 1.3. A turn that could not start shows on its board as a `turn_unstarted` notice with its reason, and `/v1/status` shows whether the engine answered the runner's last call, and which runtime images are missing. Serve reaches the engine through its socket, so serve's user is in the engine's `docker` group, which is root on the host in effect: give the platform a host, or a virtual machine, of its own. `examples/two-instances/` is what a first deployment copies: two instances of one tenant on one Linux host under systemd, their units, one shared clone of the configuration repository, and how to build, keep and trim the runtime images in serve's image store, which a deployment backs up. `examples/deployment.yaml` shows the runner's block in its Docker variant.

Make the sockets directory owned by serve's user, in the sandboxes' group, with mode 0750, which that group can traverse, or 0755; systemd's `RuntimeDirectoryMode=0750` does so, with serve's own group, the sandboxes' by default. Serve refuses one it does not own, or that its group or others can write, such as the 0775 a plain `mkdir` makes under umask 002, which Debian and Ubuntu give a user with a private group. Name it in `runner.docker.sockets` by its resolved path, such as `/run/agentswarm/a`, not `/var/run/agentswarm/a` on Debian and Ubuntu, where `/var/run` is a link to `/run`: every sandbox mounts the path as given, which the engine resolves again at each sandbox's creation, so serve refuses a path with a link in it, naming the path to give. The directory's path, and every one of its parents, must be writable by root or serve's user alone: serve's checks at its start cannot catch a parent swapped after them, before its bind or before a later sandbox's creation.

`make image` builds the runtime image of a commit, `IMAGE_COMMIT`, `HEAD` by default, from the commit alone, and prints its id, which goes in `runner.images`: one commit gives one image id on one engine. `make image-dev` builds the worktree's own runtime image, which the gates' sandboxes run. Each image build leaves a record of about 35 MB in BuildKit's cache, which no later build reuses: `docker buildx du` shows the records, and `docker buildx prune --filter until=24h` removes those older than a day. A prune is engine-wide, and takes other projects' build caches on the engine too.

`make test-image` builds one commit twice, and checks that the two builds give one binary and one image id. `make test-linux` runs the suite on Linux, in a test container on the Docker engine: `make test` and `make test-integration`; the e2e suite under the Docker runner; and, under the process runner, the scenarios that check a process is gone. `make test-docker` runs the Docker path alone: the Docker runner's integration tests, serve's tests of it, and the whole e2e suite under the Docker runner. Both run in a test container named for the worktree, `agentswarm-test-<id>`, and refuse at once while a container of that name exists: a run of the worktree is going on, or a killed one left it. Once no run is live, remove a stale one with `docker rm -f agentswarm-test-<id>`, as the refusal says, with the id. Both build the test image, and the worktree's own runtime image and stubborn test image, each under a tag of the worktree's, and the harness takes the Docker runner from `AGENTSWARM_E2E_RUNNER=docker`, with `AGENTSWARM_E2E_IMAGE` and `AGENTSWARM_E2E_STUBBORN` set to the two images' ids, and runs each `go test` of the e2e suite under a tenant of its own, `AGENTSWARM_E2E_TENANT`. Every target that builds an image needs the Docker CLI's buildx plugin, which a Linux host may lack: on Debian and Ubuntu, the `docker-buildx-plugin` package of Docker's apt repository. `make test-linux` and `make test-docker` mount `/srv/agentswarm-e2e` at the same path inside and outside the test container, since serve's sockets and the sandboxes' mounts must share that path: on a Mac they need OrbStack, in whose engine's VM `/srv` resolves, as Docker Desktop does not share `/srv`. On a Linux host they make `/srv/agentswarm-e2e` as root, through a container, and give it to you. `make test-clean` leaves it in place, and the test container's cache volumes, `agentswarm-test-gomod` and `agentswarm-test-gocache`, too.

Every container a test starts carries the label `agentswarm.project=agent-swarm`. A test run that is killed leaves its containers behind: `make test-clean` removes this project's containers that have run for over an hour, after it saves each one's `docker inspect` output and its labelled data under `.test-clean/`, as `<id>-<UTC start>.inspect.json` and `<id>-<UTC start>-data.tar`, which no later run replaces. Run it between test runs, as it cannot tell a run still going from one that was killed; `go run ./test/testclean -dry-run` shows what would go. `make test-compat` is the test against the previous release: it runs that release's harness scenarios 1, 2 and 8, from a worktree at its tag, against a schema this build migrated, then has this build verify the audit chain and inspect each item they left. The previous release is the latest release tag in HEAD's history, such as `v0.1.0`; a pre-release such as `v0.2.0-rc.1` does not count. It needs Docker, and backs up its Postgres container under `.test-clean/` before it removes it. Until a release is tagged, it prints `no release tagged; nothing to check` and passes, and at the first release's own commit it prints `no release before <tag>; nothing to check`. It checks a promise, that the previous release can read the schema this build leaves, which only migrations an older build can ignore may make: when the schema's `min_reader` is above the previous release's level, its last migration's number, it prints `<tag> cannot read the schema this build migrated (its level <level> is below the schema's min_reader <min_reader>); deploy in Decision 18's order: stop the older instances, migrate, then start the new build; nothing to check` and passes without running the scenarios.
