## Implementation

Go, with domain-driven design and interface-driven ports and adapters. See Section 2.2 of the platform specification.

Build and test with `make build`, `make test`, `make test-integration` (needs Docker), `make test-e2e` and `make test-live`. `make test-live` plays one turn of the agent runtime through the LLM gateway against the model vendor: it needs `AGENTSWARM_LIVE_KEY`, the vendor's key, and costs a few cents. Run it, and commit `internal/llm/endpoint/testdata/live-check.json`, whenever the anthropic-sdk-go version changes (`make test` fails until then), and before agents switch model (set `AGENTSWARM_LIVE_MODEL` to the new model).

`make test` also runs the coordinator's interleaving test, in `internal/work/app`, on its default schedules. Two instances, each the real leader over the real coordinator, share in-memory fakes of every store, clock and port, and seeded schedules drive them through acts and previews, lost answers and failed writes, a lease lost in the middle of an act, failed renewals, drains, crashes and takeovers, kill switch rows written out of band, and steps of the database's clock and of each instance's wall clock, forward and back, up to 10 minutes, though the database's clock steps forward by less than the lease's margin within a lease's term; reads also fail, on their own or after a write to the same store has failed or lost its answer (a record store's `Load`, `Active` and `UnstaffedBy`, the board's `Load` and the kill switch's reads, each per instance). The lifecycle's ten invariants are checked each at its own point: the tenth, that nothing runs for a closed item, at every call that starts work, and after every event; most of the others after every event, or after every batch of events in the concurrent mode, and two only once the schedule has settled, that every run alive at an on-row was halted, and that a stopped run leaves nothing running. The default run, 200 sequential schedules of 200 events and 20 concurrent ones from a base seed fixed in code, takes about 8 to 12 seconds under `-race`. The seeds recorded for Plan 7b-1's version of the test no longer replay, since the world now draws more faults. A failure prints its seed, the tail of its event log, the invariant it broke, and the command that runs it again, `go test -race -count=1 -run '^<test>$' ./internal/work/app/ -args -interleave.seed=<seed>`, in the test's own mode: a sequential schedule replays event for event, while a concurrent one replays its choice of events and faults, not their timing, so its command runs it 20 times. The soak run, `go test -race -count=1 -v -timeout 60m -run '^(TestRandomSchedulesKeepTheLifecyclesInvariants|TestConcurrentSchedulesKeepTheLifecyclesInvariants)$' ./internal/work/app/ -args -interleave.for=40m`, runs schedules for 40 minutes, half sequential and half concurrent, from a base seed of the clock's, which each test logs, unless `-interleave.base` gives one.

`agentswarm registry validate --dir DIR` checks a configuration repository against every loader rule; `examples/config/` is a fictional team's repository. `agentswarm registry hash-tools --endpoint URL` prints each of a server's tools with the whole definition that a server registration pins, and its schema hash; `--ca FILE` trusts a CA bundle besides the system roots.

`agentswarm migrate` applies the database's migrations to the database the libpq environment variables name (`PGHOST` and the rest), or to the one `--secrets DIR --database REF` names. Migrations are expand-only: each records the oldest build that can read the schema it leaves, and one that older builds cannot read is refused while an instance holds the lease, unless `--force` is given. `agentswarm serve --deployment FILE` runs one instance of the platform: the coordinator, the leader, which holds the platform's lease, both gateways, and the admin API on loopback, with the deployment file of Plan 7d-1's Contract C1; `examples/deployment.yaml` is a commented example, and `bench/itbench/README.md` runs the mechanism check's investigators on one scenario under serve. Of several instances, one leads at a time, and the others stand by. SIGINT or SIGTERM drains it under the lease it holds; a second signal stops every turn and exits at once. Serve logs at its start the longest its drain can take, as `worstDrain` in its `serve started` line, `1m37s` with the default timings: a supervisor's stop timeout must stay above it. Its runner runs each turn with `agentswarm turn`, the agent runtime, which reads its turn's spec on standard input: in a Docker sandbox, with `runner.kind: docker` (below), or, for development and tests, as a host process, with `runner.kind: process`. The process runner runs turns unsandboxed, so serve allows it only with `runner.unsafeNoSandbox: true`, and only with the gateways' listeners on loopback, since they serve it plain HTTP. `agentswarm inspect --deployment FILE item ID`, `board RUN` or `calls RUN` prints, as JSON lines, what the database holds of an item, a run's board or a run's calls. `agentswarm conclude --board FILE` assesses a recorded board offline. It decodes the file strictly, so a build older than Plan 7d-2 refuses a board whose `turn_unstarted` notice holds a `reason`: conclude such a board with this build or a later one.

Each work item has a lifecycle (spec Section 4.1). Past `lifecycle.investigating` items investigating at once, 3 by default, a new item waits in the queue, and starts in its turn. The admin API acts on items: `POST /v1/items/{id}/promote` starts a waiting item at once, even past the limit by one, or staffs an item that awaits its close with no run; `POST /v1/items/{id}/close` closes an item from any state, and stops its run mid-round; and `POST /v1/items/{id}/reopen` reopens a closed item within `lifecycle.reopenWindow`, 24 hours by default. Each takes an `Idempotency-Key` of 1 to 128 printable ASCII characters, under which a retry answers as the act did, and an optional body, `{"reason": {"code": "...", "text": "..."}, "preview": true}`: a preview takes no key, and answers the act's consequences while it does nothing. An item awaiting its close closes by itself after its work item type's `autoClose.after`, 30 minutes by default. `GET /v1/kill-switch` shows the kill switch, and `POST /v1/kill-switch` turns it on or off, with `{"on": true, "after": <seq>, "reason": {"code": "..."}}`: `after` is the latest row its sender read, 0 before the first, so that a delayed request never undoes a newer one, and the on needs a reason. The on stops every run at once, and staffs no item, while auto-close pauses, until an admin turns it off; the off lists the items the on left unstaffed, which a person promotes. A draining serve still takes the on, recorded under its holding for the next leader to act on. A refusal of these routes is `{"error": "...", "code": "..."}`. An extension of a run is `POST /v1/items/{id}/extend`, with a body of `rounds`, `wallClock` (a duration with its unit; a bare `"0"` is refused, though the deployment file's `lifecycle.extension` accepts a quoted one) and `tokens`, at least one above zero: it raises a running run's budget, and resumes a stopped run on its own board, a refusal `stopping` (`503`, with `Retry-After: 1`) while the run is stopping and `409` with `not_started`, `no_agents_left` or `would_stop_at_once` when it cannot. `POST /v1/items/{id}/link`, with `{"with": "<item id>"}`, joins an item into the incident of another, and `POST /v1/items/{id}/unlink` separates it; each needs a reason, and answers `400` `self` for a link of an item to itself and `409` `rulings_window_passed` for a closed item past `lifecycle.closedRulings`. `GET /v1/items/{id}` shows an item's place in the queue, why it is not staffed, when it closes by itself, and its close; `/v1/status` shows the kill switch and the queue. A write of the kill switch whose answer is lost may have landed: until a read of the switch settles it, serve starts no work, as if the switch were on, and a promotion answers `503`, to be sent again; close, reopen, previews and reads go on. Serve logs `kill switch unsettled` as this begins and `kill switch settled` when a read ends it, at most a retry wait, 5 seconds by default, once the database answers again. A turn already running or launching when an on-row committed keeps its session until then.

Alerting sources open items through the inbound listener, `listeners.inbound`, an optional `host:port` on loopback behind the deployment's TLS proxy (spec Section 3.6), which should rate-limit `/inbound/`: each request that names a known source costs a read of its secret file, an HMAC over a body of up to 4 MiB and a Warn line. A source posts a JSON body to `POST /inbound/{source}`, signed: `X-Agentswarm-Timestamp` holds the request's time in decimal Unix seconds, and `X-Agentswarm-Signature` one or more `v1=<64 lowercase hex characters>`, comma-separated, each HMAC-SHA256 by the source's secret over the signed string `<timestamp>.<raw body>`. The secret is the file its trigger mapping's `hmacSecretRef` names, of one line, or two during a rollover, read at each request. A request is refused `401 bad_signature` when no current secret signed it, `401 stale` when its timestamp is more than the mapping's `maxAge`, 5 minutes by default, from the database's time, `404 unknown_source` for a source no mapping maps, `400 scheme_unsupported` for a mapping that authenticates by a bearer token, until the onboarding build, and `413 too_large` for a body over 4 MiB, unread when its declared length exceeds the limit; nothing is recorded for any of them. An authenticated body is refused, with one refused record keyed by the body's SHA-256, `400 bad_body` when it is not JSON, `413 too_many_events` when it splits into more than 500 events, and `400 no_events` when its mapping's split selects none. A mapping's `maxAge` is at most 1 hour. The mapping, a `TriggerMapping` of `examples/config/trigger-mappings/`, splits the body into events, each of which is a repeat, late, appended to an open item that holds its instance, its dedup key or its correlation key, a resolution that matches no item, or a new item's opening, through the queue, the kill switch and the daily cap; an event a mapping cannot route is recorded with its reason and a Warn line naming the mapping's owner. A `200` gives each outcome's count, `{"opened": 1, "appended": 0, "late": 0, "repeat": 0, "resolved_unmatched": 0, "unroutable": 0, "refused": 0}`, once every event has one; a `503`, with `Retry-After: 1`, asks the source to send the whole request again, and the events already taken come back as repeats. Once every alert of an item resolves, its run stops `trigger_resolved` at its round's end, and the item closes by itself after its `autoClose.after`; it never closes by itself while an alert fires. A firing for an item awaiting its close resumes its run at once, or is declined with a code on its record; a firing after the close opens a new item linked into the closed item's incident. Each event appended to an item after its opening is posted on its running board as platform evidence. Until Plan 7c-2, a mapping's `principal`, `responders` and `fallbackPrincipal` are not applied, a mapping with `checks` refuses its events, and only an admin acts on an item a source opened.

A person opens an item's board at `/items/{id}`, signed in through the web interface (a `web` block of the deployment file). The board is generated by rules: a header with the item's state and stop reason, its conclusion and the conclusion's status word, the budget used, the suggestions and the alert's instances; the incident's other items with their conclusions, flagged when they disagree; the hypotheses ranked, each with up to two quotes a side and its suggestions beneath; and the feed, which merges the board's entries with the item's records, platform evidence, and notices. It refreshes by conditional polling every 5 s, not by a stream, so it needs no HTTP/2 and survives a deploy or a takeover: one embedded script, `live.js`, with no inline code and a content security policy of its own, fetches the page's regions and replaces those that changed; without the script the page says to reload it. Every stored text is shown inert, in a box when it is free text, so it cannot pass for the platform's words. An item's principal and responders open the raw output of each tool call from the feed, decoded as an outline when it is JSON, with numbered lines, the quotes that cite it marked, and its first 256 KiB; anyone else gets `404`, and until Plan 7c-2 no one sees the raw outputs of an item a source opened. Board reads go through a pool of two connections of their own, which serve opens with the `web` block, so no viewer takes the coordinator's connections; the kill switch's page and its POST keep the main pool.

Upgrading to this build: migration 0010 adds the kill switch's table, and no older build can run on the schema it leaves, so stop the older instances, migrate, then start the new build, which is downtime with two instances. Migration 0011, like 0010, declares no older reader, so an upgrade from the build before it (Plan 9a-1) needs the same stop, migrate and start, and so does migration 0012, the inbound events' table, from the build before it (Plan 7c-1a). A rollback is then a roll forward, or a restore from a backup, which loses what was written since. A restore can also lose an on-row of the kill switch: read the switch after a restore, and turn it on again if an on was lost. The anchor owner's read-only role, with which `agentswarm audit anchor` and `audit verify` read the chain, needs `SELECT` on `kill_switch`. The deployment's `tenant` must be of the anchors' form, 1 to 63 lowercase letters, digits and dashes, the first not a dash, and serve refuses to start while the environment gives `MCPGODEBUG` a non-empty value. The registry now refuses a key value listed inline that holds a character a reader could miss, tab and line feed included: remove any such value from the configuration repository before upgrading, since an open item locked at a commit that holds one cannot rebuild its revision under the new rule. The admin token stays the loopback break-glass, with the subject `admin`: it now authorizes every lifecycle act, promotion, close and reopen, extending, linking and unlinking, and the kill switch's on and off, besides openings: it acts as an admin, and an on stops every run. Under the process runner a turn runs as serve's user and can read the secrets directory, the admin token's file included, which the Docker runner keeps out of a turn's reach. An older build's `agentswarm conclude` refuses a board that holds a `skill_yanked` notice, for its new field: conclude such a board with this build. It also refuses a board that holds a `resume` entry, which the coordinator posts when an extension resumes a stopped run, and the build before this one (Plan 7c-1a) refuses one whose `resume` entry a firing caused: conclude such a board with this build too. The first takeover after the upgrade arms the auto-close of every older item awaiting its close, and those already past their deadline close one by one, just after it.

Upgrading to a build with Plan 9a-2 (the live board) needs no migration, but the worst drain rises 5 s for every deployment, a `web` block or not: serve's `worstDrain` counts the web's pool, so it is `1m42s` with the default timings, not `1m37s`. A supervisor's stop timeout set close to the old figure is checked against it; the example unit's `TimeoutStopSec=120` still clears it, by 18 s. The registry now refuses a write tool's `summary` that holds a character a reader could miss, as a zero-width space, a bidi control, or the variation selector U+FE0F that follows many emoji: remove any such character from the configuration repository, and let the items locked at a commit that holds one close, before upgrading, since such an item cannot rebuild its revision under the new rule.

The Docker runner, on Linux alone, runs each turn in a sandbox: a container of the runtime image the item locked, with no network, which reaches the gateways through two Unix sockets in `runner.docker.sockets`, over TLS 1.3. A turn that could not start shows on its board as a `turn_unstarted` notice with its reason, and `/v1/status` shows whether the engine answered the runner's last call, and which runtime images are missing. Serve reaches the engine through its socket, so serve's user is in the engine's `docker` group, which is root on the host in effect: give the platform a host, or a virtual machine, of its own. `examples/two-instances/` is what a first deployment copies: two instances of one tenant on one Linux host under systemd, their units, one shared clone of the configuration repository, and how to build, keep and trim the runtime images in serve's image store, which a deployment backs up. `examples/deployment.yaml` shows the runner's block in its Docker variant.

Make the sockets directory owned by serve's user, in the sandboxes' group, with mode 0750, which that group can traverse, or 0755; systemd's `RuntimeDirectoryMode=0750` does so, with serve's own group, the sandboxes' by default. Serve refuses one it does not own, or that its group or others can write, such as the 0775 a plain `mkdir` makes under umask 002, which Debian and Ubuntu give a user with a private group. Name it in `runner.docker.sockets` by its resolved path, such as `/run/agentswarm/a`, not `/var/run/agentswarm/a` on Debian and Ubuntu, where `/var/run` is a link to `/run`: every sandbox mounts the path as given, which the engine resolves again at each sandbox's creation, so serve refuses a path with a link in it, naming the path to give. The directory's path, and every one of its parents, must be writable by root or serve's user alone: serve's checks at its start cannot catch a parent swapped after them, before its bind or before a later sandbox's creation.

`make image` builds the runtime image of a commit, `IMAGE_COMMIT`, `HEAD` by default, from the commit alone, and prints its id, which goes in `runner.images`: one commit gives one image id on one engine. `make image-dev` builds the worktree's own runtime image, which the gates' sandboxes run. Each image build leaves a record of about 35 MB in BuildKit's cache, which no later build reuses: `docker buildx du` shows the records, and `docker buildx prune --filter until=24h` removes those older than a day. A prune is engine-wide, and takes other projects' build caches on the engine too.

`make test-image` builds one commit twice, and checks that the two builds give one binary and one image id. `make test-linux` runs the suite on Linux, in a test container on the Docker engine: `make test` and `make test-integration`; the e2e suite under the Docker runner; and, under the process runner, the scenarios that check a process is gone. `make test-docker` runs the Docker path alone: the Docker runner's integration tests, serve's tests of it, and the whole e2e suite under the Docker runner. Both run in a test container named for the worktree, `agentswarm-test-<id>`, and refuse at once while a container of that name exists: a run of the worktree is going on, or a killed one left it. Once no run is live, remove a stale one with `docker rm -f agentswarm-test-<id>`, as the refusal says, with the id. Both build the test image, and the worktree's own runtime image and stubborn test image, each under a tag of the worktree's, and the harness takes the Docker runner from `AGENTSWARM_E2E_RUNNER=docker`, with `AGENTSWARM_E2E_IMAGE` and `AGENTSWARM_E2E_STUBBORN` set to the two images' ids, and runs each `go test` of the e2e suite under a tenant of its own, `AGENTSWARM_E2E_TENANT`. Every target that builds an image needs the Docker CLI's buildx plugin, which a Linux host may lack: on Debian and Ubuntu, the `docker-buildx-plugin` package of Docker's apt repository. `make test-linux` and `make test-docker` mount `/srv/agentswarm-e2e` at the same path inside and outside the test container, since serve's sockets and the sandboxes' mounts must share that path: on a Mac they need OrbStack, in whose engine's VM `/srv` resolves, as Docker Desktop does not share `/srv`. On a Linux host they make `/srv/agentswarm-e2e` as root, through a container, and give it to you. `make test-clean` leaves it in place, and the test container's cache volumes, `agentswarm-test-gomod` and `agentswarm-test-gocache`, too.

Every container a test starts carries the label `agentswarm.project=agent-swarm`. A test run that is killed leaves its containers behind: `make test-clean` removes this project's containers that have run for over an hour, after it saves each one's `docker inspect` output and its labelled data under `.test-clean/`, as `<id>-<UTC start>.inspect.json` and `<id>-<UTC start>-data.tar`, which no later run replaces. Run it between test runs, as it cannot tell a run still going from one that was killed; `go run ./test/testclean -dry-run` shows what would go. `make test-compat` is the test against the previous release: it runs that release's harness scenarios 1, 2 and 8, from a worktree at its tag, against a schema this build migrated, then has this build verify the audit chain and inspect each item they left. The previous release is the latest release tag in HEAD's history, such as `v0.1.0`; a pre-release such as `v0.2.0-rc.1` does not count. It needs Docker, and backs up its Postgres container under `.test-clean/` before it removes it. Until a release is tagged, it prints `no release tagged; nothing to check` and passes, and at the first release's own commit it prints `no release before <tag>; nothing to check`. It checks a promise, that the previous release can read the schema this build leaves, which only migrations an older build can ignore may make: when the schema's `min_reader` is above the previous release's level, its last migration's number, it prints `<tag> cannot read the schema this build migrated (its level <level> is below the schema's min_reader <min_reader>); deploy in Decision 18's order: stop the older instances, migrate, then start the new build; nothing to check` and passes without running the scenarios.

The unattended browser gate (Plan 9a-3) lets a person or an AI agent walk the board's browser checklist with no click. `make browser-gate` needs Chrome for Testing at the pinned version (157.0.8103.78, macOS on Apple silicon), Docker, and about an hour. Get the browser once, under `~/Library/Caches/agentswarm/chrome-for-testing/157.0.8103.78/`; the two targets below fail at once, before any build, and print these commands when it is missing:

```
mkdir -p "$HOME/Library/Caches/agentswarm/chrome-for-testing/157.0.8103.78" && cd "$HOME/Library/Caches/agentswarm/chrome-for-testing/157.0.8103.78"
curl -fsSLO https://storage.googleapis.com/chrome-for-testing-public/157.0.8103.78/mac-arm64/chrome-mac-arm64.zip
curl -fsSI https://storage.googleapis.com/chrome-for-testing-public/157.0.8103.78/mac-arm64/chrome-mac-arm64.zip | grep -i x-goog-hash
openssl dgst -md5 -binary chrome-mac-arm64.zip | base64
ditto -x -k chrome-mac-arm64.zip .
```

The two hashes must agree before the zip is unpacked; for this version the MD5 is `v7Jfs/ZyxPL7I2rKuPVSGw==`. The harness refuses any browser bundle other than Chrome for Testing, and never launches the installed Google Chrome, whose crash handler would write into your own Chrome directory. The browser runs with its crash database in the run directory, kept off the network, and trusting only the environment's own leaf certificates. `make test-browser` runs the harness's own tests with that browser.

`make browser-gate` serves the e2e environment for `AGENTSWARM_BROWSER_GATE` minutes, 100 by default, and runs the browser in it, signed in. Each run gets a directory of its own, `<UTC time>/`, under `AGENTSWARM_BROWSER_GATE_OUT`, which is `.browser-gate` in the checkout by default. The run opens a control socket there, `control.sock`, through which a controller drives the browser. It keeps the evidence there too, and at its end its verdict, `verdict.txt`. The log goes to `last.log`, beside the run directories; its `The run's verdict:` line is the run's own verdict, and the next run replaces it. A run's socket must fit the 103 bytes macOS binds a Unix socket at, so `AGENTSWARM_BROWSER_GATE_OUT` may be at most 73 bytes, its links resolved. From a longer checkout, such as a worktree's, name a shorter directory, as in `make browser-gate AGENTSWARM_BROWSER_GATE_OUT=$HOME/.browser-gate`; the gate checks it before anything starts.

The environment prints the socket's command sheet itself, so it is not repeated here. The walk is Plan 9a-3's [The gate's walk](plan/2026-11-12-plan-9a3-unattended-browser-gate.md#the-gates-walk): Plan 9a-2's checklist, [The browser gate](plan/2026-11-10-plan-9a2-live-board.md#the-browser-gate), in an order that keeps the faults apart. `POST /end` ends the run early; a command with no body needs `curl -X POST`, since a bare curl sends a GET, which answers 405. A run killed with Ctrl-C while the walk has an instance stopped by `kill -STOP` leaves that `agentswarm serve` stopped: find it with `pgrep -fl "agentswarm serve"`, then `kill -CONT <pid>` and `kill <pid>`. What stays manual: Safari, the iPhone, and assistive technology.
